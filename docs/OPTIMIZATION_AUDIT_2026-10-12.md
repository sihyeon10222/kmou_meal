Story는 요청 해석 → 식당 조회 → 렌더링 → 선택적 장식 → Supabase → Instagram → 실행 기록 순서다. 실패한 식당 이후에도 다음 식당을 처리한다. 주간은 성공 기록 확인 → 조회 → 미래 추가 판정 → 과거 메뉴 동결 → 렌더링 → 잠금 및 게시 기준 재확인 → 업로드/게시 → 성공 기록 → 교체 알림 순서다.

`.github/actions/setup`은 Node 24·npm 의존성·Chromium을 설치한다. `ci.yml`은 검증, `daily.yml` / `weekly.yml`은 수동/외부 dispatch 진입점이다. 두 게시 workflow의 공통 concurrency 그룹과 기존 예약 입력·Secrets는 변경하지 않았다. 이번 작업은 GitHub·Instagram에 실제 알림이나 게시물을 전송하지 않았다.

런타임 의존성 6개는 모두 사용한다: Supabase SDK(저장소), Cheerio(HTML 파싱), dotenv(설정), Playwright(렌더링), Sharp(변환/합성), Undici(학교 조회 전용 연결 제어). dev 의존성의 ESLint/typescript-eslint는 설치만 되어 있어 이번에 실제 검증에 연결했다. 패키지 버전과 lockfile은 유지한다.

## 4. 성능 측정

Node **24.19.0**, macOS arm64, 같은 설치 의존성·Chromium·내장 폰트·고정 식단을 사용했다. 다른 성능 측정이나 전체 테스트와 겹치지 않게 순차 실행했다. 준비 실행 1회 후 5회 중앙값이며 파일 저장과 결과 해시 계산도 시간에 포함한다. 원시 표본과 SHA-256은 [측정 JSON](OPTIMIZATION_BENCHMARK_2026-10-12.json)에 보관했다.

| 측정 범위 | 변경 전 | 최종 변경 후 | 관측된 감소 |
| --- | ---: | ---: | ---: |
| 주간 전체: 통합 2페이지 + 두 생활관 파노라마 | 2,337.52 ms | 2,050.42 ms | 12.3% |
| 장식기를 사용하지 않는 Story 4장 | 1,979.36 ms | 1,843.17 ms | 6.9% |
| 31일×3행 모의 응답에서 7일 조회를 200회 | 22.78 ms | 19.92 ms | 12.6% |

식단 처리의 절대 절감은 200회당 약 2.86ms로 작다. 이를 주요 운영 병목으로 주장하지 않으며, 네트워크 응답시간 절감 수치도 아니다. 실제 HTTP·Supabase·Instagram·Cloudflare 요청은 측정에 포함하지 않는다.

주간 전체 한 배치의 Chromium 실행은 **4회 → 1회**다. Story 4장에서는 소비하지 않는 PNG 캡처 **4회 → 0회**다. 준비 실행까지 포함한 전체 벤치마크에서는 Chromium 30회 → 12회, PNG 48회 → 24회, 최종 Story JPEG는 24회로 같다. 미리보기 스크립트의 주간 12페이지도 한 브라우저를 공유한다.

두 번째 중간 측정에서는 주간 2,116.89ms, Story 1,868.52ms였으며, 표에는 연결 종료 복구까지 반영한 최종 코드의 측정을 썼다. 로컬 표본의 변동이 있어 이 비율을 다른 호스트나 실제 게시 전체의 고정 성능 향상으로 일반화하지 않는다. SDK 지연 로드·장식 중복 계산 제거의 개별 시간과 프로세스 전체 메모리 사용량은 별도로 측정하지 않았다.

최종 비교한 **72개 이미지(12종 출력 × 준비 포함 6회)는 모두 변경 전과 바이트 단위 SHA-256이 일치**했다. Story의 PNG 생략 효과는 장식기가 없는 경로에 한정하며, 장식 옵션이 있는 실제 기본 Story 흐름의 성능 수치로 제시하지 않는다.

재현 명령:

```bash
npm run benchmark -- before
# 비교 대상 코드를 적용한 다음

```

이전 커밋에서 재측정할 때는 신규 `scripts/benchmark.ts`를 그 체크아웃에 복사하고 `npx tsx scripts/benchmark.ts before`로 실행할 수 있다. 재사용 렌더러가 없는 버전도 측정하는 호환 경로가 포함되어 있다. 출력 경로와 각 이미지 해시는 `results.json`에 남는다.

## 5. 유지보수·안정성 개선

브라우저 관리를 한 모듈로 모아 지연 시작, 시작 실패 후 재시도, 연결 종료 후 재생성, 중복 close, 시작 중 close를 같은 정책으로 처리한다. DOM/context는 이미지마다 별도로 만들고 닫는다. 기존 `renderStory`와 `renderWeekly` 함수의 인자·반환 형식은 유지하며, 배치 호출자만 새 주간 렌더러를 사용한다.

새 추상화는 두 렌더러가 공유하는 브라우저 수명과 기존 네 곳의 끼니 생성에 한정했다. 학교와 Instagram의 서로 다른 재시도 정책이나 Story/주간 게시 상태 흐름은 합치지 않았다. 주간 성공 기록을 잠금 안에서 다시 읽는 것도 동시 게시 방지에 필요한 조회이므로 중복 요청으로 삭제하지 않았다.

`tsconfig.check.json`은 소스·테스트·스크립트를 검사하고, 기존 `tsconfig.json`은 소스만 빌드한다. 불필요한 지역 변수·인자 검사를 활성화했다. ESLint recommended 검사와 `npm run lint`를 추가했으며, 스타일 전체 재포맷이나 새 의존성 도입은 하지 않았다.

- 학교·Supabase·Instagram·GitHub·Cloudflare의 실제 운영 요청은 새로 실행하지 않았다. 외부 서비스와의 계약은 모의 응답 및 로컬 전송 테스트로 검증했으며, 운영 계정의 게시 성공 여부까지 재검증했다고 주장하지 않는다.

## 7. 남긴 개선 후보와 이유

- **학교 조회 병렬화/연결 재사용**: 현재 응답에 여러 날짜가 함께 오므로 무작정 병렬화하면 캐시가 채워지기 전 중복 조회가 늘 수 있다. 학교 서버의 stale socket 문제에 대한 기존 fresh-connection 정책과 재시도는 유지했다.
- **Instagram 생성·게시 병렬화/대기 축소**: 순서·기록·중복 게시 방지와 외부 API 지연 정책에 영향을 준다. 실서비스 검증 없이 적용하지 않았다.
- **장식의 파생 PNG·합성 결과 추가 캐시**: 버전·해상도·배치에 따른 무효화와 메모리/디스크 증가가 필요하다. 현재 재생성 비용을 막는 원본 캐시는 유지하고, 입증되지 않은 추가 캐시는 만들지 않았다.
- **글자 측정 알고리즘 변경**: 픽셀 단위 여백과 줄바꿈에 민감하다. 확인된 불필요 캡처와 브라우저 실행부터 줄이고 레이아웃 계산은 유지했다.
- **주간 snapshot 깊은 복사 제거·추가 인덱스**: 자료량이 작고 과거 기록의 불변성이 중요하다. 복잡성 대비 이득이 입증되지 않았다.
- **브라우저 메모리 튜닝**: 재사용 브라우저는 게시 대기 중에도 살아 있으므로 유지 시간은 길어진다. 이미지별 context는 즉시 해제하지만, 전체 프로세스 peak RSS 절감은 측정하지 않았고 주장하지 않는다. 더 짧은 프로세스 수명과 시작 비용 사이 선택은 실제 운영 프로파일을 바탕으로 판단할 수 있다.
